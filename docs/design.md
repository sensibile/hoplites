# 설계 초안

## 목표와 경계

Hoplites의 최종 목표는 보안 증거와 라이선스 의무 이행을 연결하는 배포 관리 시스템입니다. 현재는 기존 도구를 조정하는 실행 계층과 아티팩트-SBOM 연결을 검증합니다. [방향과 언어 기준](project-direction.md)을 따릅니다. 새로운 SAST 엔진이나 취약점 데이터베이스를 만들지 않습니다. 첫 단계에서는 로컬 저장소와 이미지 산출물을 대상으로 하는 일회성 실행을 다룹니다. 웹 UI, 멀티테넌시, 자동 수정, Kubernetes 클러스터 접근은 초기 범위 밖입니다.

## 실행 흐름

대상 지정 → 실행 계획 → 도구 실행 → 원본 산출물 수집 → 결과 정규화 → 정책 판정 → 보고서.

실행기는 명시적으로 선택한 도구만 실행합니다. 대상, 도구 버전, 옵션, 시작 및 종료 시각, 종료 코드, 제한 시간을 기록합니다. 비밀 값과 자격증명은 인수나 보고서에 기록하지 않습니다. 저장소 코드와 빌드 스크립트는 신뢰하지 않으며, 빌드나 코드 실행이 필요한 분석은 별도 실행 경계를 요구합니다.

## 어댑터의 책임

각 어댑터는 지원 대상, 명령 구성, 성공 및 발견 종료 코드, 출력 형식, 버전 범위, 파싱을 정의합니다. 실행기는 제한 시간과 산출물 보관을 담당합니다. 정책 계층은 심각도, 예외, 허용 라이선스 같은 판정만 담당합니다.

도구의 원본 진단을 보존하면서 공통 필드로 변환합니다. 서로 다른 도구의 결과가 의미상 같다고 가정하지 않습니다. 중복 후보는 표시할 수 있지만 첫 구현에서는 자동으로 제거하지 않습니다.

## 서로 다른 증거

SBOM은 구성요소 목록이며 취약점 발견 항목과 분리합니다. 서명 검증은 대상 digest, 검증 시점, 신뢰한 키 또는 identity/issuer 조건과 함께 기록합니다. 검증 성공만으로 대상 코드의 안전성을 판정하지 않습니다.

Kubernetes 매니페스트 검사와 실행 중인 클러스터 또는 노드 검사는 대상과 권한이 다릅니다. 후자는 별도 실행 모드와 명시적 접근 설정이 필요합니다.

## 실패와 판정

도구 실행 상태: succeeded, failed, timed_out, skipped.
정책 판정: pass, fail, indeterminate.

발견 항목이 있는 성공 실행과 도구 실행 실패를 구분합니다. 필요한 도구가 실패하거나 결과가 불완전하면 전체 결과를 pass로 만들지 않습니다. 취약점 DB 버전과 갱신 시점을 확보할 수 없는 경우 unknown으로 표시합니다. 발견 항목이 없다는 결과는 실행한 도구와 대상 범위 내의 증거입니다.

## 구현 전 결정할 사항

웹앱·서버는 Elixir, 복잡한 CLI는 Rust, 스크립트와 실험은 Python으로 구현합니다. 배포 방식, 최초 지원 도구 버전, 실행 격리 방식, 취약점 DB 갱신 방식, 산출물 보관 및 민감정보 삭제 정책, 외부 네트워크 접근 조건을 첫 실행 기능 구현 전에 결정합니다.

## Dependency-Track 연동 후보

Dependency-Track을 선택적 SBOM 분석 및 의존성 지속 관리 서버로 검토합니다. Hoplites는 SBOM 생성과 다양한 보안 점검 실행을 담당하고, Dependency-Track에는 승인된 대상의 CycloneDX SBOM을 전달합니다. 상세 검토와 실험 기준은 [검토 문서](dependency-track.md)에 있습니다.

연동 상태는 업로드 접수, BOM 처리, 분석 결과 확보를 구분합니다. 업로드 접수만으로 정책 판정을 통과시키지 않습니다. 프로젝트 버전, SBOM digest, 분석 시점, 서버 버전과 원본 결과를 기록하여 일회성 검사와 지속 분석 결과의 차이를 추적합니다. Dependency-Track 정책과 Hoplites의 전체 점검 정책을 분리하고 예외 처리의 권위는 연동 구현 전에 정합니다.
