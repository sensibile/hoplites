# 새 이미지 처리 작업 지침

새 이미지나 버전의 처리는 기존 파이프라인과 축적한 규칙을 실제로 적용하고 부족한 부분을 확장하는 작업이다. DT에 구성요소를 등록하는 것은 이 과정의 한 단계다. 작업 요청이 짧아도 아래 기준을 임의로 생략하지 않는다. BOSS가 특정 단계만 요청했다면 수행 범위와 남은 단계를 명시한다.

## 1. 맥락과 실행 기반 확인

AGENTS.md, [프로젝트 방향](project-direction.md), [비교 기준](sbom-comparison.md), [파이프라인](image-pipeline.md), [사용 가이드](usage-guide.md), [ADR](adr/README.md)과 유사한 이미지의 실험 기록을 읽는다. 스크립트만 읽고 목적과 완료 기준을 추정하지 않는다.

원격 main/source SHA와 관련 PR의 OPEN/MERGED/CLOSED 상태를 확인하고 실행 checkout의 branch/HEAD와 대조한다. 병합된 작업의 후속 개발은 최신 원격 target을 기준으로 새 worktree에서 수행한다. 여러 worktree 중 먼저 발견한 디렉터리를 고르지 않는다. 기존 산출물을 조회할 때도 생성 코드 SHA와 현재 코드의 차이를 확인한다.

작업 시작 시 대상 이미지·플랫폼, 재사용할 패키지/런타임 어댑터와 규칙, 알려진 미지원 사항, 이번 완료 범위를 명시한다. 원격 상태를 확인하지 못하면 최신 코드라고 주장하지 않는다.

## 2. 동일 아티팩트의 원본과 비교본 수집

첫 실행은 업로드 없이 검토용 산출물을 만든다. 예시:

```sh
python3 scripts/image_pipeline.py python:3.13-slim-bookworm \
  --platform linux/arm64 --trivy --output-dir artifacts/python-slim-review-001
```

입력 tag, index와 플랫폼 manifest digest, image/rootfs hash, 스캐너 index/child digest·버전·옵션, 실행 시점과 오류를 보존한다. Syft와 Trivy가 같은 플랫폼 digest를 검사했는지 확인한다. 새 이미지·버전 실험에는 Trivy가 필수다. 실패하면 원인을 해결하고 재실행한다. 외부 장애로 실행 불가능하면 비교 미완료로 남기며 이미지 처리 완료라고 보고하지 않는다.

CLI는 Trivy 비교 BOM을 생성하지만 항목별 비교 보고서를 자동으로 만들거나 Trivy findings를 DT에 병합하지 않는다. 에이전트는 아래 교차검증을 별도로 수행해야 한다.

## 3. 기존 정규화 적용과 부족분 해결

패키지 DB와 rootfs를 기준으로 OS 패키지의 버전·아키텍처·소유 관계를 확인한다. 파일은 원본에 보존하고 검증된 소유 패키지·해시에 따른 제외만 정규화본에 적용한다. 파일 이름이 같다는 이유로 제외하지 않는다. 플랫폼 정보와 설치 DB 등의 분류에는 기존 규칙을 적용한다.

패키지 밖에 설치된 런타임과 포함 코드도 조사한다. Python slim의 Python처럼 OS 패키지로 설치되지 않은 런타임은 실제 설치 파일·release marker·라이선스 문서·빌드 출처를 확인하고, 가능한 버전·라이선스를 표준 필드에 채운다. pip 등 언어 패키지, 런타임 내부 코드와 패키지 소유 파일을 혼동하지 않는다. 라이선스 표현의 AND/OR/WITH 관계와 예외는 원문 근거로 보존한다.

기존 규칙이 적용되지 않으면 그 이유를 확인한다. 새로운 버전/설치 방식/별칭을 새 SQL migration 또는 어댑터로 추가하고 재실행한다. 실제 입력을 대표하는 회귀 검증과 관련 기존 이미지의 회귀 확인을 남긴다. 이미 적용한 migration을 수정하거나 BOM JSON을 일회성으로 고쳐 규칙 누적을 대신하지 않는다.

미해결 항목은 이름·버전·PURL/bom-ref, 문제, 조사한 근거, 확인 상태, 다음 확인 방법으로 기록한다. 같은 원인의 묶음은 해당 구성요소 목록을 연결한다. `NOASSERTION`, 빈칸, 경고는 조사 결과의 표현일 뿐 조사 생략이나 의무 면제의 근거가 아니다. 확인할 수 있는 필드는 채우고 나머지는 추정/미해결로 구분한다.

## 4. Syft·Trivy 교차검증

원본끼리, 정규화 Syft와 Trivy를 각각 비교한다. 파일 개수 차이와 패키지/런타임 차이를 분리한다. 이름만으로 병합하지 않고 생태계·PURL·버전·아키텍처를 사용한다.

| 비교 범위 | 기록할 내용 |
| --- | --- |
| OS 패키지 | 설치 DB 대비 누락, 한쪽만 식별된 항목, 버전·아키텍처 차이 |
| 런타임·언어 의존성 | 직접 설치 런타임, pip 등 패키지, 포함 코드의 식별 차이 |
| 메타데이터 | PURL, 버전, SPDX ID/식·자유 텍스트 및 라이선스 누락/충돌 |
| 파일·제외 | 정규화 제외가 개수 차이를 설명하는지, 미해결 파일과 실제 소프트웨어 구분 |
| CVE | 취약점 ID, 구성요소 식별, advisory 출처, 영향/수정 버전, DB 시점과 미검출 원인 |

차이마다 확인된 원인과 아직 모르는 원인을 구분한다. 총 개수나 CVE 개수만으로 도구의 우열을 정하지 않는다. Trivy 결과가 없다는 이유로 DT finding을 suppression하지 않는다. 배포판 패치 판정은 정확한 vendor 버전과 advisory 근거로 한다. 기존 VEX 어댑터가 적용되면 수집·판정·적용 후 상태 재조회를 수행한다. 미지원 배포판은 미지원과 다음 구현 범위를 기록한다.

## 5. 업로드와 제출 증적

로컬 정규화·교차검증·제출 번들 확인 후 업로드한다. 재실행은 새 출력 디렉터리에 동일한 고정 digest와 플랫폼을 사용한다. tag를 다시 해석해 다른 이미지를 같은 실험이라고 기록하지 않는다. 미완료 결과를 조사용으로 등록할 경우 전체 작업을 완료로 표시하지 않는다.

DT 이벤트 완료를 기다리고 전체 페이지에서 식별·개수·버전·라이선스 등 기존 검증 필드를 확인한다. BOM 개수와 DT 개수가 다르면 병합 전 구성요소의 위치·hash·필드·의존 관계가 손실되는지 조사한다. 이름·버전이 같다는 설명이나 unique identity 개수만으로 검증 실패를 통과시키지 않는다. 해결된 동등성/병합 정책은 규칙·검증 코드와 증거로 누적하고 재검증한다. 기존 실패 증적은 보존한다.

원본/보강 BOM, 변경·제외 사유와 근거, 적용 migration/스크립트, rootfs/image hash, 교차검증 보고, DT 전후 검증 및 적용한 VEX 근거를 연결한다. hash manifest와 제출 번들을 확인하고 실험 기록은 docs에 누적한다. API 검사와 UI 검사, 정보 보강과 실제 의무 이행의 완료 여부를 각각 기록한다.

## 6. 완료와 인계

| 단계 | 완료 증거 |
| --- | --- |
| 수집 | 동일 플랫폼 digest의 Syft·Trivy 원본과 스캐너/실행 조건 |
| 정규화·보강 | 적용 가능한 기존 규칙 실행, 새 차이의 조사·규칙 반영, 표준 필드 확인 |
| 교차검증 | 항목별 차이 목록, 원인·조치·미해결과 후속 확인 방법 |
| 제출 증적 | 원본/결과/변경·제외·출처·규칙·해시의 연결과 번들 확인 |
| DT | 접수/처리와 전체 구성요소·표준 필드 검증, 실패 원인 해결·재검증 |
| CVE/VEX | 실제 판정 범위와 근거, 해당 시 적용·재조회, 미지원/미해결 명시 |

각 단계의 상태를 완료/미완료/범위 밖으로 보고한다. 미해결이 있으면 부분 완료로 인계할 수 있으나, 수행하지 않은 조사나 실패한 검증을 완료로 바꾸지 않는다. 인계에는 절대 worktree 경로, branch/코드 SHA, 이미지 digest, 산출물 경로, 단계별 상태, 남은 항목과 다음 실행 방법을 남긴다.

## Python slim 작업에서 확인한 기준 위반

- 실행 worktree는 `development-workflow`의 이전 구현 `3c4cb32`였고, 최신 병합본의 수정 사항을 사용하지 않았다.
- 실행에 `--trivy`가 없었고 Trivy BOM과 교차검증이 없었다.
