# Dependency-Track 검토

검토일: 2026-10-03. 공식 문서 기반 기능 검토이며 설치 및 연동 실험은 수행하지 않았습니다. 읽은 사용 및 배포 문서는 v4.14로 표시되지만 공식 홈페이지는 v5 기능을 소개합니다. 아래는 공통 역할을 중심으로 한 설계 제안이며 도입 버전과 API 계약은 구현 전에 확정합니다.

## 결론

Hoplites의 선택적 의존성 지속 관리 서버로 적합합니다. 여러 프로젝트와 릴리스의 SBOM을 모아 추적해야 할 때 도입 가치가 커집니다. 최초 로컬 Syft → Grype 실행의 필수 의존성으로 두지는 않습니다.

## 공식 문서에서 확인한 기능

- CycloneDX BOM을 수신하고 분석하며 REST API로 CI에서 업로드할 수 있습니다.
- 프로젝트와 버전 단위로 BOM을 연결할 수 있습니다.
- 구성요소의 알려진 취약점을 지속적으로 분석합니다.
- 프로젝트 또는 포트폴리오에 라이선스, 보안, 운영 정책을 적용할 수 있습니다. 라이선스 정책은 전달된 구성요소 라이선스 정보에 의존합니다.
- 컨테이너 배포가 가능하며 API 서버와 프런트엔드, 영속 데이터 저장 및 운영 관리가 필요합니다. 구체적인 DB 및 자원 요구사항은 선택 버전의 문서를 확인합니다.

## Hoplites에서의 역할 제안

| 요소 | 역할 |
| --- | --- |
| Syft | 대상에서 SBOM 생성 |
| Grype / Trivy | 명시적 실행 시점의 취약점 검사 |
| Dependency-Track | SBOM 축적, 의존성 지속 분석, 프로젝트별 관리 |
| Hoplites | 실행 조정, 결과 및 증거 연결, 전체 점검 정책 판정 |

기존 보안 점검 도구의 공통 보고서 저장소로 사용한다고 가정하지 않습니다. SAST, Secret, IaC 등은 Hoplites의 별도 결과 흐름으로 유지합니다. 또한 의존성 업데이트 PR 생성이나 소스 파일의 라이선스 발견을 이 서버 연동의 완료 조건으로 삼지 않습니다.

## 도입 비용과 경계

서버 및 DB 운영, 백업, 업그레이드, 취약점 데이터 갱신, API 인증과 권한 관리가 추가됩니다. 일회성 검사만 필요한 경우에는 이 비용의 이점이 작습니다.

SBOM에는 내부 패키지명, 버전, 구성 관계가 포함될 수 있습니다. 서버 소유자와 데이터 보관 범위를 정하고, 분석기별 외부 서비스 통신 여부를 확인해야 합니다. 자체 호스팅만으로 모든 분석이 외부 전송 없이 수행된다고 가정하지 않습니다. API 키는 소스나 실행 로그에 저장하지 않습니다.

라이선스 누락과 부정확한 구성요소 식별자는 후속 분석을 제한합니다. 취약점 결과 차이는 DB, 식별자 매칭, 분석 시점 등의 차이를 조사하고, 여러 도구의 개수를 단순 합산하지 않습니다.

## 작은 연동 실험

1. 버전과 배포 구성을 고정한 테스트 서버를 준비합니다.
2. 합성 또는 공개 대상 하나에서 지원하는 CycloneDX 버전의 SBOM을 생성합니다.
3. 프로젝트/릴리스 식별자와 SBOM digest를 기록하고 업로드합니다.
4. 업로드 접수와 후속 처리 및 분석 완료를 API 계약에 따라 구분하고 제한 시간 내 결과를 확보합니다.
5. 구성요소, 취약점, 라이선스 정책 위반을 원본 응답과 함께 조회합니다.
6. 같은 BOM 재전송 시 중복 및 상태 변화, 다른 릴리스 업로드 시 분리, 인증 오류와 서버 지연 시 indeterminate 처리를 확인합니다.

완료 증거는 대상과 결과의 연결, 재전송 동작, 오류 처리, 분석 완료 확인입니다. 지속 모니터링과 새로운 취약점 알림은 별도 장기 실험으로 검증합니다. 이 실험의 성공만으로 검출 정확도나 운영 준비 완료를 주장하지 않습니다.
